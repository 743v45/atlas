# PostgreSQL 横向评测

> 当前节点(2026 年 8 月):主流稳定版是 **PostgreSQL 18**(2025 年 9 月 25 日发布),PG 17/16 在生产中仍广泛使用。

## 一、技术架构

PostgreSQL 的架构哲学是 **"多进程 + 堆表 + MVCC + 可扩展"**,和 MySQL 的多线程 + 可插拔存储引擎走的是两条不同的路。

### 1. 进程与内存模型
- **多进程架构**:一个 `postmaster` 主进程监听连接,每个连接 fork 出一个独立的 backend 进程。
- 后果:**连接数 = 进程数**,每个连接内存开销较大(通常几 MB),这是 PG 上千连接后性能下降的根因,也是 PgBouncer 这类连接池存在的理由。
- 共享内存区:shared_buffers(数据页缓存)、WAL buffer、锁表等。

### 2. 存储引擎
- **堆表(Heap)**:数据按行存储在无序堆中,没有 MySQL 那种"聚簇索引即表"的概念——二级索引存的是行指针(CTID),不是主键值。
- **MVCC(多版本并发控制)**:更新 = 删旧版本 + 写新版本,读不阻塞写、写不阻塞读。代价是产生 **dead tuples(死元组)**,需要 **VACUUM** 回收空间(这是 PG 运维的核心痛点)。
- **WAL(预写日志)**:所有修改先写 WAL 再落盘,保证崩溃恢复(ARIES 协议)。
- **表空间**:物理存储位置抽象,可把热表放到 NVMe、冷表放到廉价存储。

### 3. 查询处理流水线
```
SQL 文本 → Parser(语法树)→ Analyzer(语义分析)→ Rewriter(视图/规则展开)
        → Planner/Optimizer(CBO 基于成本优化)→ Executor(火山模型执行)
```
- **CBO 优化器**成熟,PG 18 进一步增强了规划器。对复杂 JOIN、子查询的优化普遍优于 MySQL。
- 执行器是经典的 **Volcano 火山模型**(pull 拉取),PG 10+ 加入了并行查询,PG 18 的 **异步 I/O(AIO)** 让顺序扫描快了 2–3 倍。

### 4. 索引体系(这是 PG 的强项)
| 索引类型 | 适用场景 |
|---|---|
| **B-tree** | 默认,等值/范围查询 |
| **Hash** | 等值(PG 10+ 支持 WAL,可用) |
| **GIN** | 全文检索、JSONB、数组(多值) |
| **GiST/SP-GiST** | 地理(GIS)、范围、最近邻 |
| **BRIN** | 时序大表、物理有序数据(极省空间) |
| **HNSW/IVFFlat**(pgvector) | 向量检索 / RAG / AI |

### 5. 扩展机制(真正的护城河)
PG 的 **extension** 是一等公民,可在不 fork 源码的前提下加载新数据类型、函数、索引、甚至改写查询计划。这是 PG 生态远超 MySQL 的根本原因:
- **PostGIS**(地理)、**pgvector**(向量)、**TimescaleDB**(时序)、**Citus**(分布式)、**pg_partman**(分区)、**pglogical**(逻辑复制增强)、**pgvector**……

## 二、优点

1. **SQL 标准兼容性极高**:窗口函数、CTE(含递归)、`LATERAL`、物化视图、`RETURNING`、生成列(PG 18 支持虚拟生成列)、`MERGE` 等几乎应有尽有。
2. **数据类型丰富**:`JSONB`(比 MySQL JSON 更可索引、更快)、数组、范围类型、枚举、自定义复合类型、域类型。
3. **事务正确性强**:严格 ACID,DDL 也可事务化(建表/加列失败可回滚);隔离级别设计严谨。
4. **可扩展性无出其右**:extension 生态 + FDW(外部数据包装器,可跨库/跨数据源联邦查询)+ 多种过程语言(PL/pgSQL、PL/Python、PL/Rust 等)。
5. **查询优化器与复杂分析能力强**:多表 JOIN、复杂过滤、CTE 表现优于 MySQL;近期基准显示复杂操作下比 MySQL 快约 1.6 倍。
6. **开源 + 许可友好**:PostgreSQL License(类 BSD),无商业使用限制,可闭源二次分发(对比 MySQL 的 GPL 双轨)。
7. **社区活跃、版本迭代稳定**:30 年历史,核心代码质量极高,大版本一年一发,文档堪称典范。
8. **现代特性跟得快**:PG 18 带来 AIO 异步 I/O、原生 UUIDv7、OAuth 2.0 认证、逻辑复制增强(可从 standby 复制 + 冲突日志)、持久化统计信息。

## 三、缺点

1. **连接模型重**:多进程 → 高并发(数千连接)下内存与上下文切换开销大,强依赖连接池。
2. **写入吞吐与 MVCC bloat**:更新产生死元组,大表 VACUUM 是运维负担;长事务会阻止 vacuum 导致表膨胀(`autovacuum` 调优是玄学)。
3. **原生分布式/水平扩展弱**:单机为主,水平分片要靠 Citus、Patroni+pgbouncer 或云方案(Aurora、Neon、Supabase),不像 CockroachDB/YugabyteDB/TiDB 那样原生分布式。
4. **复制配置门槛**:流复制 + 逻辑复制两套体系,故障切换(高可用)需要外部工具(Patroni、repmgr、pg_auto_failover),不是开箱即用。
5. **并行查询成熟度**:虽已支持,但与 ClickHouse 这类分析专用引擎仍有差距;OLAP 大宽表聚合不是它的主场。
6. **调参复杂**:"tons of knobs",默认配置偏保守,生产需要大量调参(shared_buffers、work_mem、wal、autovacuum 等)。
7. **DDL 大表操作历史痛点**:加默认值列等早期会重写全表(后续版本已大幅改善),但仍需注意锁级别。

### 分组精讲

**① PostgreSQL vs MySQL(最经典的对决)**
- PG 更强:**复杂查询/分析、窗口函数、JSONB、SQL 标准兼容、扩展生态、数据正确性**。2025 年起,社区普遍认为 PG 在特性/正确性/性能上已对 MySQL 拉开明显差距且在持续扩大。
- MySQL 更强:**简单读多写少的 CRUD、运维简单、连接/复制上手快、Web 场景默认**。
- 一句话:**新项目无历史包袱 → 优先 PostgreSQL**;已有 MySQL 栈、团队熟悉、需求简单 → MySQL 仍可靠。

**② PostgreSQL vs MongoDB**
- MongoDB:无固定 schema、原生分片、文档即对象,适合快速迭代、结构多变、读多写多的内容/日志场景。
- PG 的 `JSONB` + GIN 索引已经能覆盖大多数"文档型"需求,且带 ACID 和强大查询。
- 一句话:**当你想用 MongoDB 时,先问自己 PG 的 JSONB 够不够——多半够,而且能同时享受关系建模。**

**③ PostgreSQL vs SQLite**
- SQLite 是嵌入式、零配置、单文件,适合移动端、边缘、嵌入式、单机工具。
- PG 是客户端-服务器,适合并发多用户、网络访问、高吞吐的生产服务。两者互补,不是竞争。

**④ PostgreSQL vs Oracle / SQL Server(商业 RAC)**
- Oracle/SQL Server 在**企业级高可用(RAC)、商业支持、特定行业合规、生态工具**上仍占优,但**许可成本极高**。
- PG 近年大量蚕食商业数据库市场,功能差距已大幅缩小,是去 O 的首选。

**⑤ PostgreSQL vs ClickHouse(OLAP)**
- ClickHouse 是列式、向量化、海量聚合分析的王者,日志/数仓/实时大盘远超 PG。
- PG 是行式 OLTP,做点查和事务强。**HTAP 不要指望单机 PG**,要么 Citus/PG+ClickHouse 双写,要么 NewSQL。

**⑥ PostgreSQL vs NewSQL 三剑客(CockroachDB / YugabyteDB / TiDB)**
| 产品 | PG 兼容度 | 强项 |
|---|---|---|
| **CockroachDB** | PG 线协议兼容(语法有差异) | 强一致、全球部署简单 |
| **YugabyteDB** | 深度兼容(fork 了 PG 查询层,最接近原生) | 最接近原生 PG 的分布式体验 |
| **TiDB** | MySQL 为主(PG 支持在增强) | HTAP、海量规模(数百 TB,LinkedIn 战略选型) |
- 何时选 NewSQL:**数据量/写入超过单机 PG 上限、需要跨地域多活强一致、需要弹性水平扩展**。单区域内、依赖 PostGIS/pgvector 等扩展、追求生态成熟 → 仍是 PG。

**⑦ PostgreSQL vs Redis**
- Redis 是内存 KV/缓存,毫秒以下延迟,做缓存、排行榜、消息、限流。
- PG 是持久化主存。通常 **PG(主存) + Redis(缓存)** 组合使用,而非二选一。

## 五、选型建议

| 你的场景 | 推荐 |
|---|---|
| 通用 Web/SaaS 后端、复杂业务、JSON + 关系混合 | **PostgreSQL**(默认首选) |
| 简单 CRUD、读多写少、已有 MySQL 栈 | MySQL |
| 结构频繁变化、文档/内容平台、超大规模分片 | MongoDB |
| 海量日志/数仓/实时分析 | ClickHouse |
| 数据/写入超单机上限、跨地域多活、强一致 | CockroachDB / YugabyteDB / TiDB |
| AI / RAG / 向量检索 | **PostgreSQL + pgvector** |
| 地理 / GIS | **PostgreSQL + PostGIS** |
| 时序数据 | **PostgreSQL + TimescaleDB** |
| 边缘/嵌入式/移动端 | SQLite |
| 预算充足 + 特定行业合规 + 商业支持 | Oracle / SQL Server |

**一句话总结**:PostgreSQL 是 2026 年**通用关系型数据库的"默认答案"**——功能最全、扩展生态最强、许可证最友好、正确性最高。它的主要短板(高并发连接模型、写入 bloat、原生分布式、OLAP)都有成熟的周边方案弥补(PgBouncer、Citus/TimescaleDB/pgvector、云托管、外加 ClickHouse)。除非你有明确的 NoSQL/OLAP/超大规模分布式刚需,否则 **"用 Postgres,直到它真的不够用为止"** 是当前最稳妥的技术决策。

===== USER =====
 如果给你 10 种数据库,你会优先选择哪些数据库,为什么选择数据库没有绝对的“最好”，只有最适合业务场景的“最对”。如果将市面上最主流、最具代表性的 10 种数据库摆在面前，我会根据核心技术演进和实际业务场景，将它们划分为三个梯队进行优先选择：第一梯队：核心主力（无条件优先选择）这一梯队是应用开发的基石，能解决 80% 的通用数据存储需求。1. PostgreSQL (高级关系型数据库)为什么优先： 它是目前功能最强大的开源关系型数据库。核心优势：完美的 ACID 事务支持，数据一致性极高。强大的扩展生态（如 TimescaleDB 搞定时间序列，PostGIS 搞定地理空间）。对 JSON 格式支持极好，可以当半个 MongoDB 使用。适用场景： 核心业务系统、复杂金融交易、需要严谨数据结构的项目。2. Redis (内存键值数据库)为什么优先： 现代高并发架构中不可或缺的“催化剂”。核心优势：数据存储在内存中，读写速度达到微秒级。支持 String、List、Hash、Set 等丰富的数据结构。原生支持分布式锁、发布订阅、延迟队列等高并发组件。适用场景： 缓存、Session 共享、排行榜、秒杀系统。第二梯队：场景专家（根据特定需求优先选择）当业务规模扩大、或者遇到特定数据结构时，关系型数据库会遇到瓶颈，此时优先引入以下数据库。3. MongoDB (文档型 NoSQL)为什么选择： 摆脱了传统表结构的束缚，开发极具灵活性。核心优势：Schema-less（无固定表结构），数据以类似 JSON 的 BSON 格式存储。天然契合面向对象编程，开发速度极快。自带横向扩展（Sharding）能力。适用场景： 用户画像、内容管理系统（CMS）、日志收集、需求频繁变动的初创项目。4. Elasticsearch (搜索与分析引擎)为什么选择： 传统数据库的 LIKE %keyword% 模糊查询在海量数据下会崩溃，而 ES 是文本搜索的王者。核心优势：基于倒排索引，提供毫秒级的全文检索和模糊匹配。强大的聚合分析能力（ELK 日志分析生态）。适用场景： 电商商品搜索、APP 全局检索、海量日志分析与监控。5. ClickHouse (列式分布式 OLA​​P)为什么选择： 在大数据量（亿级以上）的大宽表分析场景下，速度快到令人发指。核心优势：采用列式存储，压缩比极高。充分利用多核 CPU 并行处理，向量化执行。适用场景： 商业智能（BI）报表、用户行为数据分析、流量统计。第三梯队：领域极客（特定规模/架构下选择）这些数据库用于解决更极端、更前沿的业务痛点。6. TiDB 或 CockroachDB (原生分布式 NewSQL)为什么选择： 兼具 MySQL 的关系型协议和 NoSQL 的无限横向扩展能力。核心优势： 一主多从遇到存储瓶颈时的终极解法，支持强一致性的分布式事务，业务无感知扩容。适用场景： 海量数据的关系型业务（如大厂的支付、订单系统）。7. Neo4j (图数据库)为什么选择： 传统关系型数据库处理“多对多”的深层社交关系时，Join 操作会导致性能雪崩。核心优势： 专注于节点和关系的存储，查询复杂人际网络或关联路径时效率极高。适用场景： 社交网络、金融反欺诈风控、知识图谱。8. InfluxDB (时序数据库)为什么选择： 专门为了应对带时间戳的高频数据写入。核心优势： 极高的写入吞吐量，自带时间窗口聚合函数（如计算每 5 分钟平均值）。适用场景： 物联网（IoT）设备监控、服务器性能指标（Metrics）收集。💡 我的选型决策漏斗（总结）在实际做架构设计时，我的思考路径通常是：默认首选：用 PostgreSQL 支撑基本盘。遇到并发瓶颈：加上 Redis 做缓存。遇到文本搜索/日志需求：引入 Elasticsearch。遇到非结构化/频繁变动的数据：引入 MongoDB。遇到海量数据报表分析：将数据同步到 ClickHouse 4 个目前在行业内举足轻重、不可忽视的数据库类型：1. 向量数据库 (Vector Database) —— AI 时代的基石随着大语言模型（LLM）的爆发，这类数据库从边缘走向了绝对的舞台中央。代表产品： Milvus, Pinecone, Chroma, Qdrant为什么重要：大模型只有“短期记忆”（上下文限制）且容易“胡说八道”（幻觉）。向量数据库通过将文本、图片、音频转化为高维数学向量并进行存储，能够实现超高速的相似度检索。核心优势：专为高维向量（通常上千维）设计。提供专用的检索算法（如 HNSW），在亿级向量中找相似性只需毫秒级。适用场景： RAG（检索增强生成，即让大模型外挂公司私有知识库）、图片/视频反查、个性化推荐系统。2.
