Interview the user relentlessly until you reach a shared understanding. Map this as a **design tree**: every decision branches into the decisions that hang off it.

Work the tree in **rounds**. The **frontier** is every decision whose prerequisites are already settled: the questions you can ask _now_ without guessing at answers you haven't heard yet. Ask the whole frontier in one round: number each question and give your recommended answer. Then wait for the user's answers before the next round.

Format a round like so:

```
❓ **Q1** - **<question title>**: <question body, might be multiple paragraphs, including multiple choices>

➡️ <your recommended answer>

---

❓ **Q2** - **<question title>**: <question body, might be multiple paragraphs, including multiple choices>

➡️ <your recommended answer>
```

Each round the user answers reshapes the tree: settled decisions push the frontier outward and unblock questions that depended on them. Recompute the frontier and ask the next round. A question whose answer depends on another question still open in this round belongs to a _later_ round, not this one.

Finding _facts_ is your job, never the user's. When a frontier question needs a fact from the environment (filesystem, tools, etc.), dispatch a sub-agent to find it; don't ask the user for anything you could look up yourself. Don't block on it: a running exploration is an unsettled prerequisite, so only the questions downstream of it wait for the sub-agent to report; ask the rest of the frontier now. The _decisions_ are the user's: put each to them and wait.

The session is done when the frontier is empty: every branch of the design tree visited, nothing left silently assumed. Do not act on it until the user confirms you have reached a shared understanding.

## ⚠️ 修正：横评真正的赢家是 Claude,不是 ChatPRD

我上一条消息说 ChatPRD 在横评中胜出——读了 [Tom Leung 横评全文](https://firesidepm.substack.com/p/i-tested-5-ai-tools-to-write-a-prdheres)后发现那是搜索摘要的误导。他的原文 TLDR 是 **"TLDR: It was Claude :-)"**。真实排名：

**这对你有直接意义：你就在 Claude Code 里，横评第一名已经是你的日常工具。** ChatPRD 对你的增量价值不在生成质量，而在下面这些。

- **Success Criteria**(定性+定量)
- **Scope**(设计定稿后才填：in/out、beta 日期)
- 铁律:*"Do not add the solution here"*(方案不许写，放 Figma 里)、*用大白话，禁止术语和代号*、打印贴在团队墙上

**Linear(Nan Yu)** — 三段式，配三条写作原则：
- **Context** — 为什么做，面向所有人，永不过时
- **Usage Scenarios** — 真实发生过的使用叙事
- **Milestones** — 分阶段、先去风险；唯一“活”的部分，团队靠它对齐
- 原则：*从最高层写到细节；从最宽受众写到最窄；从最不会变的写到最会变的*

**Lenny's 1-Pager** — 最广为采用的格式：
- **Problem Statement**(最重要的段落：什么问题、谁有、怎么知道是真的)
- **Solution**(方案 + 为什么选它而不是替代方案)
- **Success Metrics**
- **Scope**(做什么 + **明确不做什么**)
- **Timeline** / **Open Questions**

### ⚖️ 中量派(2-5 页，带流程)

**Kevin Yien(Square→Stripe)** — 五阶段工作流，防“没对齐就跳到方案":
- 头部：贡献者(PM/设计/工程/数据)+ 状态追踪 **Draft → Problem Review → Solution Review → Launch Review → Launched** + 最后更新日期
- **Part 1 Problem Alignment**:问题描述、为什么重要、客户洞察、干系人签字栏
- **Part 2 Solution Alignment**:方案概述、目标、**Non-Goals**、关键流程、mockup、边界情况、签字栏
- **Part 3 Execution**:launch plan、度量、rollout 策略
- **Part 4 Appendix**:changelog、FAQ、依赖
- 灵魂：*"画解决方案空间的周界——把边界画出来，让团队专注于怎么填满它"*

**Basecamp Shape Up Pitch** — 独创 "Appetite" 概念：
1. **Problem** 2. **Appetite**(先定时间预算：“我们给这事 2 周而不是 2 个月”)
3. **Solution**(只到宏观层面) 4. **Rabbit Holes**(预判的坑) 5. **No Gos**

### 📋 全面派(完整 10 段)

**ChatPRD 官方 2026 模板** — 传统全面型的当代标准(和它产品倡导的恰好是两个流派)：
1. Overview / Problem Statement
2. Goals & Success Metrics
3. User Stories & Use Cases
4. Functional Requirements("The system shall…"句式)
5. Non-Functional Requirements(性能/安全/合规)
6. Design Considerations
7. Technical Considerations
8. Timeline & Milestones
9. Open Questions & Risks
10. Appendix

并按项目类型给定制建议：新功能→重 user stories;平台迁移→重技术+回滚策略;API→重端点/认证/限流；移动端→重离线和电量。常见错误五连：*细节过载、没拉干系人、跳过度量、写完就冻结、模糊语言(“要好用”这种)*。

**Figma(Yuhki Yamashita,Coda 版)** — 活文档枢纽：内嵌实时 Figma 设计稿(改稿文档自动更新)、交互式里程碑表、launch checklist。

**Uber** — 企业合规型：PRD Checklist + 跨产品线影响矩阵(Rider/Driver/Eats/Fleet)+ Legal/Privacy 审批字段。

### 🎯 特殊流派

**Amazon PR/FAQ(Working Backwards)** — 从结局倒写：
- **Press Release**(一页内)：标题套公式 `[公司] 发布 [产品],让 [客户] 能够 [受益]` + 假想发布日期 + 客户喜悦引言 + 高管引言
- **External FAQ**(客户和媒体会问什么)+ **Internal FAQ**(TAM、定价、竞争、技术可行性、资源)
- 特性：写作极重(数天到数周)，**大多数 PR/FAQ 被毙掉是功能不是 bug**——最便宜的想法过滤器。AWS、Kindle 都这么出来的。

**Adam Waxman(SeatGeek)** — 唯一带 **Decision Journal** 的：explored directions(探索过哪些方向)→ decided direction(定了哪个)+ 为什么。专为“干系人绕圈重翻旧账”设计——**这正好治你说的‘想清楚的东西后来忘了’**。

### 各家文化的注脚

- **Stripe**:shaping 先于 spec,工程师/PM/BD 人人写文档，“最好的想法赢，不是最响的人赢”
- **Linear**:50+ 员工只有 1 个 PM 头衔；不做 A/B 测试，“taste 驱动决策，而不是测试驱动决策”
- **Spotify DIBB**:Data → Insight → Belief → Bet,每个 bet 配两页文档
- **Meta**:PM 一年零 ticket,工程师自己管项目
