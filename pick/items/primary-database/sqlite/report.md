# SQLite

> **TL;DR**：被 pick 为嵌入式与单机场景的默认数据库：单文件零运维、部署量世界第一；但多用户并发网络服务不是它的战场——与 PostgreSQL 互补而非竞争。

- **结论**：adopt（推荐——嵌入式/边缘/单机场景默认选择）
- **核实日期**：2026-08-27

## 为什么选（在其领域）

- **零运维、零部署**：单文件即数据库，无服务端进程、无配置；移动端、桌面软件、边缘设备、CLI 工具的默认答案 [3][4]。
- **许可不可更友好**：公共领域，商用/闭源/改名分发皆可，法律层面零摩擦 [3]。
- **SQL 质量高**：SQL 标准子集实现严谨，事务 ACID 完整；FTS5 全文检索、R-Tree 空间索引内建 [3]。
- **生态在扩张**：libSQL/Turso、LiteFS、cr-sqlite 等衍生在把 SQLite 推向「本地优先（local-first）+ 边缘同步」的新赛道（taevasidian 底稿 2026-08）[4]。

## 为什么不选（出界即止）

- **并发写是硬边界**：整库级写锁（WAL 模式下读写可并发，但写仍串行），多用户高并发网络服务会撞墙——那是 PostgreSQL 的战场 [4]。
- **无网络协议、无用户权限体系**：文件即边界，不适合多进程/多租户共享服务 [4]。
- **单机分析不是它强项**：本地单机数据分析的新答案是 DuckDB（嵌入式 OLAP，taevasidian 有独立报告）[4]。

## 对比

- vs **PostgreSQL**：互补关系——客户端-服务器、并发多用户、网络访问 → PG；嵌入式、边缘、单文件 → SQLite（taevasidian 底稿 2026-08）[4]。逐维度对比见 `../comparison.md`。
- vs **DuckDB**：同为嵌入式，OLTP vs OLAP 分工（观察名单）。

## 风险与注意

- 官方仓库在 Fossil（非 GitHub），镜像延迟一般数小时内；引用代码/issue 以 sqlite.org 为准 [1][2]。
- 高并发写场景误用是常见事故来源——选型时先确认「真的只有一个写入者」。
