Mpx

TL;DR：滴滴增强型小程序框架——编译输出原生 DSL、运行时开销最小一档，复杂小程序业务的性能敏感之选；Skyline 选项式 API 可用而组合式 worklet 受限，社区声量小一档。

为什么选（作为 trial）

  • 性能≈原生的编译架构：Mpx 不引入重运行时，编译输出目标平台原生 DSL，模板转原生自定义组件、数据走编译期依赖收集驱动 setData。官方自测运行时体积（demo 总体积减 native 基线）：Mpx 51KB vs uni-app 87KB vs taro next 156KB vs kbone 368KB（评测方=Mpx 官方、约 2020 年数据，方向性参考、利益相关降权采信）[4]。第三方横评同样把 Mpx 标为「小程序复杂业务、性能敏感」选项、性能档位与原生同列（2025）[5]。
  • 对微信原生规范的完整兼容：以增强型 DSL 起家（数据响应 watch/computed、增强模板语法、跨团队 packages 开发），「小程序自身规范的完全支持」是其设计基线——原生页面/组件可低成本混用（官方 1.0 公告，2026-10-01 访问）[6]。
  • Skyline 有适配路径：维护者 hiyuki 在 issue #1454 明确回复——选项式 API 下 Skyline 组件与 worklet 动画按微信文档正常编写即可用；组合式 API 因微信编译规则暂无法使用 worklet（2024-04-25）[7]。2026-07 有「mpx skyline skill」PR 开放中（gh 2026-10-01），适配仍在推进 [8]。
  • 滴滴级业务验证：框架的复杂度上限由滴滴出行小程序矩阵背书（网约车/金融/单车多业务线）[1]。

对比

  • vs 原生：Mpx 增强语法（响应式/组合复用/状态管理）解决原生开发模式的工程化短板，运行时开销接近零；不选它的理由通常是团队已有 React/Vue 栈或多端强需求。
  • vs Taro/uni-app：三者多端能力同档（小程序多端+Web），差异在架构——Mpx 增强编译输出原生 DSL 无重运行时，性能上限高于两者的运行时/抽象层方案；代价是类 Vue 增强 DSL（非标准 Vue）带来的生态与招聘半径收窄，社区体量小一档（⭐3.9k vs 4.2 万/3.8 万，gh 2026-09-30）[1]。
  • vs morjs：同为滴滴/饿了么系「贴近原生」路线；Mpx 是增强 DSL 编译框架，morjs 是存量 DSL 互转工具，赛道不同（见 morjs 报告）。

风险与注意

  • 社区与人才池小一档：⭐3,940、npm 周下载 2,114（2026-09-22~09-28），教程/三方组件生态以滴滴系产出为主；团队离开滴滴系支持后的自我维护成本要预估 [1][3]。
  • Skyline 组合式 API 受限：worklet 在组合式 API 的 setup 中不触发（微信编译规则所致，维护者确认 2024-04），重度 Skyline 手势/动画项目需按选项式 API 写对应代码 [7]。
  • 性能测评数据老化：运行时体积对比为约 2020 年官方数据，Taro 4/uni-app 新版均有优化，结论方向可用、数值不可直接引用（待验证：三方 2026 年同版本重测）[4]。
  • 文档官网双站：mpxjs.cn 与 didi.github.io/mpx 并存（后者为旧版），检索文档时认准新版官网。
