# 记录规则（RULES）

本项目（pick — 选型对比决策库）所有报告必须遵守本规则。规则的目的只有一个：让选型**有理有据**——每个论断可追溯、每个数据有出处有日期、结论与索引元信息始终一致。

选型对象不限于软件工具：表现形式、方案、产品……任何「要从中挑一个」的东西都是一个条目（item）。

## 1. 目录与命名

- **域（domain）→ 类别 → 条目** 三层：根级 `domains.json` 定义域（`{slug, name, description, categories: [类别slug]}`），**每个类别必须归属一个域**（build 校验全覆盖/无未知）；索引页只列域，域页 `domains/<slug>.html` 装类别宽表。
- **分层判据（何时加层/拆层）**：
  - 一层值得存在 ⟺ 它回答一个别的层不回答的问题，且有独立生命周期——否则是伪层级。
  - 实践甜点 **3–4 层**；每层成本 = 面包屑 +1 跳 + 校验规则 +1 类。
  - 向上加「界」（域之上的超级分组）：**域超过 7±2 个**才触发（Miller 律，顶层列表开始需要分组）。
  - 向下加「亚种」（条目之下的变体）：**有独立 meta（独立 verdict/stats/matrix）才立条目**；只是形态差异（fork 未分家、版本演进）→ 正文小节。例：zendriver 独立立目（有独立 repo 与维护节奏），Logseq OG/2.0 不立（双轨是形态差异）。
  - 单类别膨胀到 30+ 条 → **横向拆类别**归同域（并系拆分），不加深层级。
- 目录一律 kebab-case：`items/<类别>/<条目>/`，如 `items/logging/zap/`
- 每个条目目录固定两个文件：
  - `meta.json` — 元信息，索引的唯一数据来源
  - `report.md` — 报告正文
- 每个类别目录一个 `_meta.json`；横评为可选的 `comparison.md`
- Slidev 演示放 `decks/<主题>/`，只链接报告、不复制结论（避免双头维护）

## 2. 元信息规范（meta.json）

| 字段 | 必填 | 说明 |
|---|---|---|
| `name` | ✅ | 工具显示名 |
| `verdict` | ✅ | 结论枚举，见下表 |
| `summary` | ✅ | 一句话结论，**必须与报告 TL;DR 完全一致** |
| `updated` | ✅ | 报告最后修改日，`YYYY-MM-DD` |
| `verified` | ✅ | 信息最后核实日，`YYYY-MM-DD` |
| `sources` | ✅ | 来源 URL 列表，**至少 1 条**，与报告文末来源列表对应 |
| `repo` / `homepage` / `license` | 建议 | 仓库 / 主页 / 许可证（SPDX 名，如 `MIT`、`Apache-2.0`） |
| `stats` | 可选 | 一手数据快照 `{source_repo, stars, pushed_at, license, collected_at}`，由 `scripts/refresh-stats.py` 从 gh 自动维护，**不要手改**；仅两段式 GitHub 项目仓库可刷（商业闭源项留空） |
| `matrix` | 建议 | 选型维度键值对（如 `{"许可": "MIT", "成本": "免费"}`），键须在该类别 `_meta.json` 的 `columns` 里定义；**索引宽表按列渲染这些值**——这是「多维并排对比」的数据源，值要短（词组级） |
| `tags` | 可选 | 小写标签数组 |

`verdict` 枚举（索引页显示中文徽章）：

| 值 | 显示 | 含义 |
|---|---|---|
| `adopt` | 推荐 | 默认选择，新项目可直接采用 |
| `trial` | 试用 | 值得在非关键路径试用 |
| `assess` | 评估 | 仍在调研，未下结论 |
| `hold` | 观望 | 不推荐新项目采用，报告中必须给出原因 |

类别 `_meta.json`：`{ "name": "日志库", "description": "一句话说明该类别", "order": 1, "columns": ["许可", "成本"] }`（`order` 控制索引排序，缺省排最后；`columns` 定义该类别**索引宽表**显示哪些维度列，工具 meta 的 `matrix` 按此渲染）。

## 3. 写作规范（有理有据门禁）

1. **结论先行**：报告第一节是 TL;DR——一句话结论 + verdict，与 `meta.summary` 一字不差。
2. **论断 → 证据 → 引用**：每条关键论断用 `[n]` 编号引用文末「来源」列表。没有引用的关键论断不允许存在。
3. **数据三要素与时间戳**：版本、环境（如适用）、日期。所有数据必须显式标注观测时间——star / 下载量注明采集日期（如 `gh 2026-08-27`），评测结论注明评测方与评测时间（如 `AIMultiple 2026`），价格注明查询日期。**无时间戳的数据视为无效**：技术选型里，过期数据比没有数据更危险（高 star 的死项目是最典型陷阱）。性能数据必须注明测试环境与出处；**不接受无出处的性能断言**。
4. **事实与观点分离**：数据是事实；推荐是观点，观点必须能从文中事实推导出来。
5. **不确定就标注**：写「待验证」，并在下次更新 `verified` 时补齐或删除。
6. **引用旧数据须注明其时间**，不给读者「这是现状」的错觉。
7. **知识参考类条目建议双层**：「查一个」而非「选一个」的条目（标准 / 图谱 / 速查类），在单份报告内分『常用速查』与『全量图谱』两层，常用层在前、速查规则代码块收尾；不拆成两个条目，避免内容重叠与双头维护。

## 4. 时效与更新

- `updated` ≠ `verified`：改错别字也更新 `updated`；只有重新核实过信息才更新 `verified`。
- **数据采集时间**（`stats.collected_at`）与人工核实时间分离：refresh-stats.py 每次刷新都会重置 `collected_at`。时效判定优先用 `collected_at`，无 stats 用 `verified`。
- 超过 **180 天**：索引卡片自动标「待复核」。一条命令全量刷新：`python3 scripts/refresh-stats.py && python3 scripts/build-index.py`。
- `verdict` 变更必须在报告末尾「变更记录」留一行：日期、旧 → 新、原因。

## 5. 横评（comparison.md）与决策矩阵（decision.json）

- **必须有属性对比矩阵**：条目并排成列、属性维度成行（如反检测层级 / AI 接入 / 许可 / 成本 / 自托管 / 维护状态 / star），让读者一眼看出差异；禁止只有「场景 → 条目名」的推荐表或各条目描述值的罗列。
- 逐维度对比表，每个格子的数据同样要有来源（脚注或引用各条目报告）。
- 横评结论必须与各条目报告的 verdict 一致；不一致时**先改报告，再改横评**。

**决策矩阵（可选，类别级 `decision.json`）**：属性矩阵 + 权重 + 评分 → 加权总分排序。

```json
{
  "updated": "2026-08-27",
  "weights": {"许可": 3, "成本": 3, "维护活跃": 5},
  "scores": {"条目slug": {"许可": 5, "成本": 5, "维护活跃": 4}}
}
```

- 权重与评分均 **1–5**；维度可超出 `_meta.json` 的 `columns`（如「维护活跃」）。
- 评分**不能拍脑袋**：值由属性矩阵值映射（如 Apache=5、AGPL=3、商业=2）或报告事实推导，映射口径写进 `note` 字段。
- comparison.md 里写占位 `<!--gen:decision-matrix-->`，build 时注入加权决策表（总分降序）。
- **必须保留注记**：决策矩阵只覆盖所列维度，维度外风险（如维护断层史）以各条目 verdict 为准——矩阵高分与谨慎 verdict 并存时，这不是矛盾，是两层的分工。

## 6. 页面生成（全部生成物，禁止手改）

`index.html`、各目录 `report.html`、`comparison.html` 均由脚本生成：

- **改完 meta / 报告后**：`python3 scripts/build-index.py`
  - 渲染每份 report.md 为 report.html（带面包屑与上下篇导航）
  - 渲染 comparison.md 为 comparison.html；`<!--gen:activity-table-->` 占位处自动注入从 meta.stats 生成的活跃度表（star 降序、含仓库列与采集日期）
  - 校验门禁：必填字段缺失 / `sources` 为空 / `verdict` 非法 / 日期格式错误 → 报错退出
  - 一致性校验：正文 `⭐N` 与 `meta.stats.stars` 不一致 → 警告（warn），修完再提交
- **刷新一手数据**：`python3 scripts/refresh-stats.py [--dry-run]`（gh 拉 star/push/license → meta.stats）
- **产物断言（防漂移测试）**：`python3 scripts/check.py`——链接完整性 / 模板残留 / 产物新鲜度 / 关键内容；CI 部署前必跑，本地 build 后建议跟跑
- Slidev deck（`decks/`）不自动生成：deck 引用的数据必须带采集日期，meta 更新后人工核对 deck。

## 7. 设计树（两级，同步变更）

选型的**决策路径**与**项目自身的架构决策**都是资产：不只记录结论，还记录「结论怎么来的」——哪些分叉、选了什么、为什么、谁被淘汰。

**项目级 `DESIGN-TREE.md`**（仓库根）：
- pick 项目自身的设计决策树：每个架构节点 = 问题 → 选择 → 理由（含被否方案）。
- **同步规则：任何架构级变更（新机制/新脚本/结构改动）必须当日加节点**——先改树再动手是推荐顺序；改了架构不加节点视为未完成。

**类别级 `items/<类别>/decision-tree.md`**（每类别一棵）：
- 内容：**根问题**（一句话）、**分叉与决策**（每个节点：问题 → 选择 → 理由，理由引用报告/来源）、**叶子**（指向条目）、**落选节点**（不指向条目的死分支——「为什么没选 X」的记忆）。
- 叶子行格式固定：`- 叶：[条目名](slug/) verdict`——build 解析叶子并与该条目 meta 的 verdict 比对：**不一致或条目未入树 → 警告**。改 verdict / 新增条目时必须同步树。

## 8. 新条目流程

1. 建目录 `items/<类别>/<条目>/`，从 `template/` 复制 `meta.json` 和 `report.md`
2. 调研写作（遵守第 3 节）
3. 填 `meta.json`（`summary` 与 TL;DR 一致）
4. `python3 scripts/build-index.py` 校验并重新生成索引

完成定义：build 通过 + 报告含模板全部章节 + 每条关键论断有引用。

## 9. 原始数据留档（raw/）

原始数据是一次性资产：star 会变、网页会消失、会话会被清理——**采集时同步留档，不指望二次获取**。

```
raw/<采集日期>/gh/        gh api 完整原始响应（refresh-stats.py 自动落盘，每仓库一个 json）
raw/<采集日期>/web/       网页 / WebSearch / WebFetch 的原始内容（markdown，文件名 <slug>-<域名>.md）
raw/<采集日期>/sessions/  会话提取文本（从 ~/.claude/projects/*.jsonl 导出的对话流）
```

- **采集即留档**：任何调研（人工或 subagent）取回的原始数据当场写入 `raw/<今日>/`——这是规则也是 subagent prompt 的必备条款。
- 跨日目录天然构成**时间序列**（star/push 按日快照）；同日重复采集覆盖当日文件。
- raw/ 不进任何校验门禁（它是原始层，允许松散）；进 git（资产）。
- 报告引用原始数据时，可注明 `raw/<日期>/` 路径作为「可复核出处」。
