容器内 DNS 排障三步法

TL;DR:第 0 步,exec 前先探容器里有什么工具——报错栈是 node 不代表容器里有 node 二进制;①读 /etc/resolv.conf 的 search 列表,拿到集群真实解析域;②同一服务名带/不带后缀各查一次,结果分裂即定位——配置里写的域与集群认的域不一致。DNS 域的事实来源是 resolv.conf 与解析实验,不是配置文件里的多数。
  • 状态:settled(定案)
  • 回答的问题:容器里服务域名解析失败(ENOTFOUND),怎么一步步定位?
  • 验证:2026-08-17 · GLM-5.3 · claude-code

第 0 步:先探工具,再 exec

现场首条命令就是翻车:kubectl exec 进容器直接跑 node 一行脚本做 DNS 查询,回的是 exec: "node": executable file not found in $PATH——应用语言 ≠ 运行环境,报错栈里的解释器可能只是构建期的,精简运行镜像里没有它。

先探可用工具再选查询手段:容器里看 getent / nslookup / wget 哪个在,都不在就换宿主机侧(kubectl 自带 DNS 查询能力)。工具探测本身有回显,是第一步证据。

① resolv.conf:集群认哪个域

/etc/resolv.conf 的 search 列表 = 集群 DNS 对短名自动补的后缀集合。服务全名的规范形态是 <svc>.<ns>.svc.<集群真实域>。配置文件里写的后缀若不在 search 列表里,补全规则就对不上——这一步拿的是「集群侧的事实」。

② 对比查询:一次实验证伪一个假设

同一服务名,两种写法各查一次:

容器内解析 <svc>.<ns>.svc.<配置里的后缀>   → ENOTFOUND
容器内解析 <svc>.<ns>(短形式,走 search 补全) → 解析成功,得 ClusterIP

结果分裂,一次就证伪了「服务不存在」——矛头直指配置。现场终局:所有 ConfigMap 都写着某个内部集群编号当后缀,而 resolv.conf 证明真实域是另一套;「所有配置都这么写」只说明同源同错,不是正确的证据。

配套反问同样是路标:「为什么要改成 cluster.local。明明应该是(我们的编号)」——先核对事实再改,别套模板答案;最终修正也不是换成「标准后缀」,而是统一改用短形式(同命名空间内最短可用形态)。

验证

  • 每步有可观察输出:工具探测有命令回显;resolv.conf 有 search 行;对比查询两结果并排——三步都是证据,不是推断;
  • 修后复跑同一实验:改完配置,重新 exec 同一对对比查询,与 search 一致的形态必须解析成功;
  • 别只验解析:能解析 ≠ 业务通,最后打一次真实调用(gRPC/HTTP)收尾。
