# SQLite 库文件安全迁移

> **TL;DR**:拷 SQLite 库不是拷一个文件,是三件套(`.db / .db-wal / .db-shm`)。红线两条:**WAL 0 字节才可单独拷 .db;非空 -wal 绝不能丢**。其余动作——确认无进程持有、前后各一次 quick_check、对端逐字节复验——都是把「拷完了」变成「拷对了」。

- **状态**:settled(定案)
- **回答的问题**:拷一个 SQLite 数据库文件,怎么保证数据一条不少地过去?
- **验证**:2026-08-05 · GLM-5.2 · claude-code

## 先搞清在拷什么:三件套

WAL 模式下,写操作先进预写日志(`-wal`),checkpoint 后才落主库(`.db`)——**最近的写入可能还住在 -wal 里**,`.db-shm` 是两者的共享内存索引。所以:

- `-wal` **0 字节** → 近写已全部落主库,可单独拷 `.db`;
- `-wal` **非空** → 丢它就是丢最近写入,必须三件套同传。

WAL 机制的完整讲义见 [asked/sqlite-wal](../../../../asked/items/sqlite-wal/answer.html)。

动手前先问机制再问操作——现场的用户没说「拷过去」,先问的是「这三个文件是干嘛的」「wal 是什么」。搞懂机制,红线是推出来的;不懂机制,红线是背下来的。

## 迁移流程(六步,现场顺序)

1. **认清现场**:`ls` 看清是几件套,别默认只有一个 .db;
2. **查 -wal 大小**:0 字节与否,决定走哪条红线;
3. **确认无进程持有**:`lsof` / `ps` 查库文件——有写入者时拷到的是中间态;
4. **源库校验**:`PRAGMA quick_check` 通过才出发;
5. **同传三件套**(现场:285MB,40s),不拆散;
6. **对端复验**:逐字节对比(或校验和)+ 再跑一次 `quick_check`。

每步打印耗时与结果——「拷了 40 秒」和「验了 40 秒」是两件事,都该有数。

## 验证

- **quick_check 打个对儿**:出发前源库一次,到达后目标库一次——只验一头等于没验;
- **逐字节/校验和对比**:大小相同不等于内容相同;
- **读一条最新记录**:对端打开库,读出源端最后写入的那条——直接证明 -wal 里的数据没丢;
- **计时打印**:每步 + 总耗时,异常慢本身就是信号。
