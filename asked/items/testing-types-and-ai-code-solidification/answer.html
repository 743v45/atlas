软件测试都有哪些类型?AI 生成的代码怎么固定下来?

TL;DR:测试没有穷尽的清单,但四个问题能装下一张地图——测多大一块(层次)、为什么要测(目的)、怎么测(方法)、什么时候测(阶段),冒烟测试只是「发布后第一眼」。而固定 AI 生成代码的核心只有一句:AI 干活得快,验收得照样走全套——读懂再用、用测试锁死行为、进 git 才算存在、把实现藏在你定的接口后面、连「为什么」一起留档;其中测试本身就是最强的固定剂。

*(建于 2026-10-01 当日问答,非历史恢复。)*

一、测试地图:四个问题问下来

把软件想象成一栋要交付入住的房子:测试就是对房子做的各种验收。四类验收回答四个问题。

问题 1:测多大一块?(层次)

层次通俗说法房子类比
单元测试(unit)验一个零件抽一块砖做抗压:这块砖本身合格吗
集成测试(integration)验零件怎么拼砖砌成墙后接缝牢不牢、水管和龙头拧得上吗
端到端测试(E2E)假装用户走全程从大门进,开灯、放水、点火做饭走一遍
冒烟测试(smoke)能不能跑起来通电通水,没爆管就放行——名字来自硬件:新电路板上电,不冒烟就算过第一关;广而浅,只保核心路径

问题 2:为什么要测?(目的)

  • 回归测试(regression):改了厨房,别把客厅的灯搞灭——修过的 bug 不许复活。发版前全量重跑的老测试套件就是它。
  • 验收测试(UAT):房主(业务方/用户)亲自来验收签字,交付前最后一道。
  • 性能测试——一家四口:
  • *负载(load)*:平常五口人住,水电够不够(预期流量下表现如何)
  • *压力(stress)*:过年三十口亲戚涌来,哪根线先烧(不断加压找崩溃点)
  • *浸泡(soak)*:连续住一年,水管漏不漏(长时间跑,查内存泄漏和性能衰减)
  • *尖峰(spike)*:电梯突然挤进二十人(流量瞬间暴涨时的表现)
  • 安全测试:小偷能不能翻进来(渗透测试、漏洞扫描、依赖审计)。
  • 混沌测试(chaos):主动拉掉一路电闸,看房子还能不能住(Netflix 的 Chaos Monkey 是祖师爷)。
  • 兼容性测试:换种气候、换个家具品牌还住得住吗(不同浏览器/手机/操作系统/分辨率)。
  • 恢复测试:断电重启后,房子按设计复原吗(备份可用、状态不丢)。
  • 无障碍测试(accessibility):轮椅和盲杖能不能用(读屏器、键盘导航、色彩对比度)。

问题 3:怎么测?(方法)

  • 黑盒:不给图纸只看现象(输入什么、吐什么);白盒:拿着图纸和线路图验,内部逻辑看得见。
  • 契约测试(contract):装修队和水电工之间的交接单——两边对「插座在哪、水口在哪」的理解必须一字不差(微服务之间用 Pact 这类工具固化接口约定)。
  • 快照测试(snapshot):给房间拍照存档,下次对比有没有人偷偷动过家具(UI 组件渲染结果与上次保存的基准比对)。
  • 模糊测试(fuzz):随机乱按开关、乱泼水,看会不会坏(喂随机/畸形输入找崩溃)。
  • 猴子测试(monkey):更原始的模糊——真·随机乱点一切。
  • 探索性测试(exploratory):不照剧本,像一位挑剔的亲戚到处摸,边玩边记问题(靠经验,无固定脚本)。
  • A/B 测试:两间房刷两种颜色,看访客更爱哪间(线上分流对比,偏产品实验)。
  • 突变测试(mutation):给测试做体检——故意把代码改坏一小处,如果测试照样全绿,说明这些测试是摆设,什么也没锁住。
  • 属性测试(property-based):不举具体例子,立一条规矩——「任何两个金额相加都不能为负」——让工具自己生成成百上千个例子去砸(Python 的 Hypothesis、JS 的 fast-check)。
  • 差分测试(differential):同一个输入喂给两套实现,答案不一致必有一坑(常用于验证新版本和旧版本行为一致)。
  • 静态测试:不运行代码的检查——代码评审(code review)、lint、类型检查。不运行也能抓掉一大半问题,是性价比最高的一道。

问题 4:什么时候测?(阶段)

  1. 写代码时:lint + 类型检查 + 本地单元测试(第一道闸,最便宜)。
  2. 提交时:CI 门禁——全量单测 + 集成测试,不过不合入。
  3. 发布前:回归测试 + 验收测试。
  4. 发布中:
  • *金丝雀(canary)*:新楼先放 1% 的住户进去住,没事再扩大(小流量先行)
  • *灰度*:按比例逐步放量
  • *影子流量(shadow)*:新系统跟着老系统并行跑,只看不接客
  1. 发布后:监控和告警——「住在房子里的测试」,出事先于用户知道。

金字塔不是唯一的形状

  • 测试金字塔(底宽顶尖:单元最多、E2E 最少)——传统后台服务的经典答案:越底层的测试越快越稳,越该多。
  • 测试奖杯(Testing Trophy):前端更适用——重度 mock 的单元测试收益很低,组件级集成测试才是价值最厚的一层,形状中间鼓。
  • 蜂窝模型(Honeycomb):微服务更适用——单个服务的单元测试价值小,服务之间的接口(集成)才是命门。
  • 结论:形状跟着「价值密度」走,哪里的问题最多就在哪里加厚,别把金字塔当教条。

三对最容易混

对区别一句话
冒烟 vs 健全性(sanity)冒烟广而浅(核心全过一遍),健全窄而深(只验这次改动碰过的那个点)
retest vs regressionretest 验「这个 bug 修好了没」,regression 验「别处没被带坏」
验收 vs 回归验收对外签字(符合需求),回归对内兜底(没改坏旧功能)

AI 时代新增:测 AI 本身

  • LLM eval:AI 应用的输出没有唯一正确答案,没法用「对/错」判卷——改用评测集打分:准备一批问题和期望标准,按相关性、幻觉率、格式合规度打分,像作文评分量规。
  • prompt 回归:改提示词等于改代码——老任务不许变差,所以同一套 eval 要在改动前后各跑一次对比。

二、AI 生成的代码怎么固定下来?

「固定」是什么意思

AI 写的代码有个特点:来得快,但会话一关它就「忘」了,而且它写的时候没经过你脑子里的完整设计。直接放进项目跑,等于沙滩上盖楼。固定 = 把它从「会话里的一段回答」变成「仓库里的一份资产」——有历史、有测试、有人负责、以后谁都能改。

类比:AI 像一支外包装修队,干得飞快,但你不能拎包入住——验货、上锁、办证、留图纸,一步都不能少。

七步固定法

  1. 读懂再收(验货):看不懂的代码不要收——看不懂 = 以后没法修 = 不是资产是负债。并且记住:AI 代码出了 bug,责任是你的,不是 AI 的,收下就要像自己写的一样维护。
  2. 测试当固定剂(上锁):为它写(或让它写)测试,测试过了才算验收。测试锁死的是行为——以后任何人(包括 AI 自己)改动这段代码,一旦破坏行为,测试立刻报警。自查方法用突变思想:故意改坏一处,测试不红,等于门没锁。
  3. git commit 即定案(办证):没进版本控制的代码不存在。固定下来的标志不是「能用」,是「进了仓库、进了历史」。
  4. 类型与 lint(装报警器):TypeScript/mypy 之类的类型检查、ruff/eslint 之类的 lint,把口头约定变成机器强制的约定——AI 留下的隐含假设会被静态检查当场揪出。
  5. 接口契约化(统一门锁):把 AI 的实现藏进你定义的接口(函数签名/API)后面。实现不满意可以随时推倒重新生成,接口不动,调用方就不用动——固定的是接口,不是实现。
  6. 沉淀到可复用位置(图纸进档案柜):一次性的回答留在会话里就好;值得复用的,长成 CLI 命令、脚本、配置项或服务接口。判据一句话:下次还会用到的,进代码库;只此一回的,让它随会话而去。
  7. 连「为什么」一起搬 + 防漂移(留维修手册):AI 代码的「为什么这么写」在会话里,而会话会丢——收编时用注释或 ADR(架构决策记录)把理由搬进仓库。此后 AI 再改这段代码时,用快照/golden master 基准(把当前正确输出存档比对)加锁依赖版本(lockfile),防止「越改越漂」。

一条主线

七步其实是一句话:AI 负责生成,你负责让生成物有归属——归属到接口、归属到测试、归属到版本历史、归属到文档。这和本仓的既有哲学同源:apprentice 馆「收录即定案」、conversations「可溯落地」、逻辑沉淀政策「所有逻辑往代码层推动」——值得留存的东西,必须有实文件。

速查

  • 测试四问:测多大(单元→集成→E2E→冒烟)/ 为什么(回归·验收·性能·安全·混沌·兼容·恢复·无障碍)/ 怎么测(黑盒白盒·契约·快照·模糊·突变·属性·差分·静态)/ 何时测(本地→CI→发布前→发布中→生产监控)。
  • 形状跟价值走:后台金字塔、前端奖杯、微服务蜂窝。
  • AI 代码固定七步:读懂再收 → 测试上锁 → git 定案 → 类型 lint → 契约化 → 沉淀复用 → 留「为什么」防漂移。
