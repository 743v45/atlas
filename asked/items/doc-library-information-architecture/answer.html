文档库信息架构:建 collection 还是加层级?

TL;DR:判据一句话——独立知识域 / 跨主题复用 / 权限可见性边界 → 建 collection(顶层容器,创建有成本);同域内细分 → 父文档层级(就是个父文档,成本低、可重组)。深度以「级 = 含 collection 的总深度」计:2 级平铺(同域 <7 篇)、3 级 collection→分类→文章(默认推荐、知识库甜点)、4 级封顶——再深该拆 collection 或重组。触发重组的数字:某层子项 >10 拆分组、平铺 >15 开一层、collection >50 拆两个。
载体说明:本判据成形于 Outline(自托管知识库 wiki)的层级设计,该载体已于 2026-08-25 弃用迁飞书——判据本身通用,适用于任何「顶层容器 + 文档树」结构的知识库(飞书知识库、Notion、Confluence 等同理)。

*(恢复自 2026-08-06 问答,原答骨架忠实;重组阈值以当日落盘 skill 的定稿为准。)*

一、层级模型与核心判据

Outline 的层级模型:collection(顶层容器,不可嵌套)→ 文档树(可多层父子嵌套)。「分组」不是独立概念,靠父文档 → 子文档实现。(发现这一点正是因为想把 collection 嵌进 collection 而不得。)

什么进 collection:

  • 独立知识域(如「AI 编程实践」「投资研究」各自成域)
  • 跨主题复用(多个主题都会引用的内容)
  • 权限/可见性边界(谁能看这一域)

collection 占导航一级入口、创建有成本,别为零散单篇建。

什么用文档层级:

  • 同一域内的主题细分。建分组成本低(就是个父文档),灵活、可重组。

经验法则:先有 5+ 篇同主题文章,再考虑是建新 collection 还是在现有 collection 下开分组;单篇/几篇直接平铺。

二、层级口径与深度建议

「级」= 含 collection 的总深度:

级数结构适用场景
2 级collection → 文章(平铺)同一域 <7 篇、松散笔记、快速记录
3 级(默认推荐)collection → 分类 → 文章知识库甜点;一个 collection 下有多个主题
4 级collection → 组 → 子组 → 文章主题下还有子分类(taxonomy)
上限 4 级—再深建议拆 collection 或重组,别往深堆

(对应「文档深度」不计 collection:2 级 = 深度 0、3 级 = 深度 1、4 级 = 深度 2。)

三、何时重组(阈值)

  • 某层子项 >10,或出现「杂项/其他」兜底桶 → 拆出子分组。
  • 层级 <2 且同 collection 文档 >15 → 开一层分组。
  • 某个 collection 长到 >50 篇 → 考虑拆成两个 collection。

四、命名约定

  • collection:简短名词,代表一个域(「AI 编程实践」)。
  • 父文档(分组):表「分类名」,名词短语(「提示词优化」「部署」)。
  • 叶子文档:表具体内容标题,不要在标题里重复上层路径——有层级了,别写「AI 编程实践-提示词优化-XXX」。

五、决策流程

这篇属于哪个已有 collection?
├─ 没有 → 内容够独立 + 预计 5+ 篇?建新 collection;否则丢进最相近的现有 collection(平铺)
└─ 有 → 该 collection 下有几个相关主题?
   ├─ 0-1 个 / 总共 <7 篇 → 平铺(2 级)
   └─ 多主题 → 开/复用一层分类(3 级)
      └─ 分类下还要再分?→ 4 级,到顶别再深

案例回放:一篇「AGENTS.md 八条规则」的文章 → 域是「AI 编程实践」(新 collection,后续会有多篇)→ 主题是「提示词优化」(开一层分类)→ 文章挂分类下 = 3 级,正是默认甜点结构。
